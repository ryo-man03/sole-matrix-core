# SOLE//MATRIX Core v0.2 Development Plan

## 1. v0.2の目的

v0.2の目的は、Core v0.1を「テスト済みライブラリ」から「使い方が分かる最小デモ」へ進めることです。

v0.1で固定した推薦ロジック、スコア計算、Decision、Demotion、Snapshot、Golden Testを壊さず、利用者が次の流れをローカルで確認できる状態にします。

1. サンプルのスニーカーデータを用意する
2. サンプルの好み・所有靴データと組み合わせる
3. Coreの公開APIを通じて推薦結果を得る
4. AIなしのルールベース説明文で、なぜその判断になったかを読む

v0.2ではWeb UI、DB、AI、外部API、デプロイはまだ入れません。Coreの信頼性を保ったまま、CLIまたは簡易デモで挙動を確認できる状態を優先します。

## 2. v0.2で実装する機能

- Coreの公開API整理
  - v0.1の内部モジュールをそのまま直接呼び出す状態から、利用者が参照しやすい入口を整理する。
  - 既存の計算式、Decision、Demotion、Snapshotの仕様は変更しない。
  - 公開対象の型、関数、戻り値を明確にする。
- サンプルスニーカーデータ整理
  - デモ用のスニーカー候補データを小さく固定する。
  - 実在価格や外部サービスに依存せず、Coreの入力として扱える静的データにする。
  - v0.1のGolden Test fixtureとは目的を分け、期待値固定用fixtureを安易に変更しない。
- CLIまたは簡易デモ
  - `pnpm` から実行できる最小デモを追加する。
  - サンプルの好み、所有靴、候補スニーカーを使って推薦結果を表示する。
  - 表示内容は、順位、finalScore、Decision、Demotion、主要なscoreBreakdown、Snapshot参照に絞る。
- AIなしのルールベース説明文生成
  - Coreの出力をもとに、固定ルールで短い説明文を生成する。
  - 説明文は確率的生成ではなく、テスト可能な決定的ロジックにする。
  - Decision、Demotion、scoreBreakdownに基づき、購入判断の理由を簡潔に示す。
- READMEへのデモ手順追加
  - v0.2実装時に、READMEへローカルデモの実行手順を追加する。
  - 今回の計画追加ではREADMEは変更しない。

## 3. v0.2で実装しない機能

- Web UI
- DB
- APIサーバー
- ログイン、認証、ユーザー管理
- OpenAI APIなどのAI連携
- 外部価格API連携
- 非公式な自動収集
- 実店舗・ECサイトのリアルタイム在庫確認
- 画像認識
- デプロイ
- 課金

- Coreの計算式変更
- `finalScore`の仕様変更
- `Decision`の仕様変更
- 既存Golden Testの期待値変更

## 4. 推奨ファイル構成

v0.2実装時は、Core本体とデモ用コードの役割を分けます。以下は実装時の推奨構成であり、今回追加するファイルではありません。

```txt
src/
  index.ts
    # Core公開APIの入口。既存ロジックの再exportまたは薄いwrapperに限定する。

  demo/
    sampleSneakers.ts
      # デモ用の候補スニーカーデータ。
    sampleScenario.ts
      # デモ用の好み、所有靴、候補一覧の組み合わせ。
    explainRecommendation.ts
      # AIなしのルールベース説明文生成。
    runDemo.ts
      # CLIまたは簡易デモの実行入口。

  domain/
    recommendation/
      # v0.1のCoreロジック。計算式・Decision・Demotion・Snapshotは変更しない。
```

テストを追加する場合は、デモ用ロジックとCore仕様固定用テストを混ぜないようにします。

```txt
src/demo/__tests__/
  explainRecommendation.test.ts
  runDemo.test.ts
```

## 5. 実装順序

1. Core公開APIの整理
   - 既存モジュールの依存関係を確認する。
   - 利用者向けに公開する型・関数を決める。
   - Core計算式を変えずに、入口だけを整理する。
2. サンプルスニーカーデータの追加
   - デモで使う候補を3から5件程度に絞る。
   - 入力値はCoreの型に合う静的データにする。
   - Golden Test fixtureとは別管理にする。
3. CLIまたは簡易デモの追加
   - サンプルシナリオを読み込み、Coreの公開APIで推薦結果を計算する。
   - 出力は人間が読めるテキストまたはJSONにする。
   - パッケージスクリプト追加が必要な場合は、Coreの動作確認後に最小限で行う。
4. ルールベース説明文生成の追加
   - Decision、Demotion、scoreBreakdownから説明文を生成する。
   - 同じ入力から必ず同じ説明が出るようにする。
   - 過剰な自然言語生成ではなく、購入判断の根拠を短く示す。
5. READMEへのデモ手順追加
   - v0.2実装後に、デモ実行コマンドと期待される出力例を追加する。
   - READMEは実装が通ってから更新する。

## 6. テスト方針

- 既存テストは変更しない。
- 既存fixtureの期待値は変更しない。
- Core計算式、`finalScore`、`Decision`、`Demotion`、`Snapshot`の仕様固定テストを壊さない。
- 公開API整理では、既存のCore結果と同じ結果が得られることを確認する。
- サンプルデータは型が満たされることを重視し、期待値固定用fixtureとは分ける。
- 説明文生成は決定的な文字列または構造化結果としてテストする。
- CLIデモは、最低限「実行できる」「主要な結果が出力される」ことをテストする。

実装後に必ず実行するコマンド:

```bash
pnpm test
pnpm typecheck
git diff --stat
git status
```

期待する結果:

- 既存テストがすべて成功する
- typecheckが成功する
- Coreロジックに変更がない
- fixtureや期待値に変更がない
- README更新はv0.2実装が通った後だけ行う

## 7. GitHubでのcommit単位

v0.2は小さく分けてcommitします。推奨単位は次の通りです。

- `docs: add v0.2 development plan without changing core`
  - v0.2計画とAgent Promptのみ追加する。
  - 差分は`docs/**`のみ。
- `feat: expose core recommendation api`
  - Core公開APIの入口を整理する。
  - 計算式や期待値は変更しない。
- `feat: add static sneaker demo data`
  - デモ用の静的サンプルデータを追加する。
  - Golden Test fixtureとは分ける。
- `feat: add local recommendation demo`
  - CLIまたは簡易デモの実行入口を追加する。
  - Coreの公開APIを使って結果を表示する。
- `feat: add rule based recommendation explanations`
  - AIなしの説明文生成を追加する。
  - 決定的なテストを追加する。
- `docs: add v0.2 demo instructions`
  - READMEへデモ手順を追加する。
  - 実装・テストが通った後に行う。

## 8. 想定リスク

- 公開API整理のつもりでCore内部仕様を変えてしまう
  - 対策: 既存テストとGolden Testを変更せずに通す。
- デモ用サンプルデータとGolden Test fixtureの役割が混ざる
  - 対策: `src/demo/`など別の場所で管理する。
- 説明文生成がCore仕様とずれて、ユーザーに誤解を与える
  - 対策: Decision、Demotion、scoreBreakdownに基づく固定ルールだけを使う。
- CLIデモのためにpackage設定が大きく変わる
  - 対策: 既存のTypeScript / pnpm / tsx構成に合わせ、最小限の追加にする。
- README更新が実装より先行して、動かない手順を書いてしまう
  - 対策: デモ実装とテスト完了後にREADMEを更新する。
- v0.2で範囲を広げすぎる
  - 対策: UI、DB、AI、外部連携、デプロイはv0.2に入れない。
