# SOLE//MATRIX UI-02: Candidate Sneaker Check Spec

## 1. Candidate Sneaker Checkの目的

Candidate Sneaker Checkは、ユーザーが気になっているスニーカーを手入力し、その候補が自分の`PreferenceProfile`と合うか、購入判断の材料になるかを確認するための画面である。

この画面は「買うべきか」を断言する購入指示ではなく、Core推薦ロジックが返す`finalScore`、`rawDecision`、`finalDecision`、`demotions`を、ユーザーが冷静に見られる形で表示する判断補助として設計する。

スニーカー名とブランド名は表示用の情報であり、スコアの根拠にしない。スコアに関係する入力は、選択された特徴タグ、入力金額、予算から後続実装で`SneakerCandidate`へ変換される値に限定する。

## 2. Preference Diagnosisとの違い

Preference Diagnosisは、ユーザーの好みを作る診断である。質問への回答から`PreferenceProfile`の初期値を作り、以降の推薦に使う土台を用意する。

Candidate Sneaker Checkは、すでに存在する`PreferenceProfile`に対して、ユーザーが気になっている1足の候補を照合する画面である。好みそのものを作る画面ではなく、候補スニーカーを`SneakerCandidate`としてCoreへ渡し、Coreの結果を表示する画面として扱う。

UI-02ではGemini説明表示を扱わない。Gemini Adapterが存在していても、Geminiの文章、AI説明文、AIによる判定補助はUI-03以降のResult / Detail設計で扱う。

## 3. 画面構成

入力は3ステップに分ける。

1. Step 1: 基本情報
2. Step 2: 特徴タグ
3. Step 3: 確認

共通構成:

- ヘッダーに`SOLE//MATRIX`と画面名`Candidate Sneaker Check`を表示する。
- 上部に現在ステップを表示する。
- ステップ番号だけでなく、`基本情報`、`特徴タグ`、`確認`のテキストも表示する。
- メイン領域は入力フォームまたは確認内容を表示する。
- 下部に主要アクションを置く。
- `戻る`、`次へ`、`診断する`のボタン状態をステップと入力状態に応じて切り替える。

結果画面は、入力ステップとは別の表示状態として扱う。UI-02では結果画面に表示すべき情報の方針までを定義し、詳細なResult / Detail体験やGemini説明文はUI-03以降で設計する。

## 4. 入力ステップ

### Step 1: 基本情報

ユーザーが気になっているスニーカーの表示情報と価格・予算の参考値を入力する。

表示する入力:

- スニーカー名
- ブランド
- 入力金額
- 予算
- メモ

ステップ遷移ルール:

- スニーカー名が空の場合は次へ進めない。
- 入力金額が未入力または0以下の場合は注意を出す。
- 予算が未入力または0以下の場合は注意を出す。
- 金額と予算の注意が出ていても、後続仕様で許容する場合は確認ステップで再確認する。ただしCoreへ渡すための必須値が不足する場合は`診断する`を無効にする。

価格に関する注記例:

> この金額はユーザー入力です。市場価格や在庫を保証するものではありません。

### Step 2: 特徴タグ

候補スニーカーの特徴を、固定の日本語ラベルのチップから選択する。

表示するタグ:

- クラシック
- ローテク
- ストリート
- シンプル
- ボリューム感
- ランニング系
- バスケット系
- 履きやすい
- 長く履けそう
- レトロ
- 文化背景あり
- 上質・高級感

ステップ遷移ルール:

- タグは1個以上選択しないと次へ進めない。
- タグは最大5個まで選択できる。
- 5個選択済みの状態では、未選択タグを追加できない。
- 選択済みタグは再度押すと解除できる。

### Step 3: 確認

Coreへ渡す前に、ユーザーが入力内容と変換方針を確認する。

表示する確認:

- 入力内容の確認
- 選択タグの確認
- 価格・予算の入力確認
- 所有靴との被り確認
- Coreへ渡す`SneakerCandidate`の確認
- `診断する`ボタン

`SneakerCandidate`確認では、表示用のスニーカー名、内部タグ、`priceLevel`、`budgetFit`の変換後の目安を表示する。ブランドとメモはUI上の補助情報として保持してよいが、現行`SneakerCandidate`には含めない。

## 5. 入力項目

| 項目 | 必須 | 用途 | Coreスコアへの扱い |
| --- | --- | --- | --- |
| スニーカー名 | 必須 | 画面表示、結果表示、ユーザー確認 | 名前そのものをスコア根拠にしない |
| ブランド | 任意 | 画面表示、ユーザー確認 | ブランド名そのものをスコア根拠にしない |
| 入力金額 | 条件付き必須 | `priceLevel`と`budgetFit`の目安を作る | 金額そのものを`finalScore`へ直接入れない |
| 予算 | 条件付き必須 | `budgetFit`の目安を作る | 予算そのものを`finalScore`へ直接入れない |
| メモ | 任意 | ユーザー用の覚え書き | スコア根拠にしない |
| 特徴タグ | 必須 | `SneakerTag[]`へ変換する | タグとしてCoreへ渡す |

入力値の保持はUIの責務である。ただし、DB永続化、アカウント紐付け、外部APIとの照合はUI-02の対象外とする。

## 6. タグ選択ルール

- タグは最大5個まで。
- 1個以上選択しないと次へ進めない。
- 英語の内部タグはUIに直接出さない。
- UIでは日本語ラベルを使う。
- 内部では`SneakerTag`へ変換する。
- AIがタグを推定しない。
- ブランド名やスニーカー名からタグを自動決定しない。
- 自由入力タグは使わない。
- Coreに存在するタグであっても、UI-02の候補タグ一覧にないものはこの画面では選択肢として出さない。

| UI表示 | 内部タグ |
| --- | --- |
| クラシック | `classic` |
| ローテク | `low_tech` |
| ストリート | `street` |
| シンプル | `minimal` |
| ボリューム感 | `chunky` |
| ランニング系 | `running` |
| バスケット系 | `basketball` |
| 履きやすい | `comfortable` |
| 長く履けそう | `durable` |

| 文化背景あり | `heritage` |

## 7. 金額の扱い

入力金額は、ユーザーが入力した参考値として扱う。

UIで行うこと:

- 入力金額をユーザー入力値として表示する。
- 予算と比較して`budgetFit`の目安を作る。
- 入力金額の大きさから`priceLevel`の目安を作る。
- 価格に関する注記を表示する。

UIで行わないこと:

- 市場価格として表示しない。
- 相場として表示しない。
- 最安値として表示しない。
- プレ値として表示しない。
- 在庫情報と結びつけない。
- 外部サイト価格や購入リンクを表示しない。
- 真贋、在庫、流通量、値上がり予測と結びつけない。

UI文言例:

> この金額はユーザー入力です。市場価格や在庫を保証するものではありません。

価格・予算との相性は`budgetFit`として扱う。`priceLevel`は靴側の価格帯、`budgetFit`はユーザー予算との相性、`priceSensitivity`はユーザー側の慎重さとして扱う。

## 8. priceLevel / budgetFit変換方針

UI-02では変換方針を定義するだけで、関数実装はしない。Coreの最終スコア式も変更しない。

基本方針:

- 入力金額そのものを`finalScore`へ直接入れない。
- 入力金額と予算から`budgetFit`を作る。
- 入力金額の大きさから`priceLevel`を作る。
- `priceSensitivity`は`PreferencePolicy`側の値として扱う。
- `priceLevel` / `budgetFit`の変換表はUI設計上の仕様であり、今回は関数実装しない。
- 実装は後続Promptで行う。
- Core実装時には既存の`priceScore`仕様と矛盾しないように扱う。

`budgetFit`の目安:

| 入力金額 / 予算 | `budgetFit`目安 |
| ---: | ---: |
| 0.7以下 | 95 |
| 1.0以下 | 80 |
| 1.2以下 | 60 |
| 1.5以下 | 40 |
| 1.5超 | 20 |

この表はUI設計上の目安であり、Core実装時には既存の`priceScore`仕様と矛盾しないように扱う。

`priceLevel`は靴側の価格帯を0から100の範囲で表す。入力金額が高いほど`priceLevel`は高くなる設計とするが、具体的な金額レンジと数値テーブルは後続実装Promptで固定する。UI-02では、市場価格ではなくユーザー入力金額をもとにした価格帯であることだけを明示する。

確認画面では、以下のように説明する。

- `priceLevel`: 入力金額から作る靴側の価格帯目安
- `budgetFit`: 入力金額と予算の比率から作る予算相性目安
- `priceSensitivity`: 診断で作られたユーザー側の価格慎重さ

## 9. 所有靴との被り

所有靴との被りは、選択タグと所有靴の`roleTags`から判断する前提にする。

UI-02では所有靴DBがないため、まずは確認欄として扱う。実際の永続化、所有靴管理、所有靴DBとの照合はCore v1.0以降に回す。

確認欄で想定する表示:

- 選択タグと所有靴の特徴が近い可能性を示す注意。
- `似ている所有靴があるかもしれません。購入前に手持ちの靴と役割が被らないか確認してください。`
- 所有靴情報がない場合は、`所有靴データがないため、被りは参考表示のみです。`

UIが行わないこと:

- UIは`overlapPenalty`を勝手に計算しない。
- UIはCoreが返した`demotions`を隠さない。
- UIは所有靴との被りを理由に`finalDecision`を変更しない。
- UI-02では所有靴をDBに保存しない。

## 10. 結果表示方針

結果は「買え」ではなく「判断材料」として表示する。

結果画面で表示するもの:

- スニーカー名
- `scoreBreakdown.finalScore`
- `rawDecision`
- `finalDecision`
- `demotions`
- 合う理由
- 注意すべき理由
- 価格・予算との相性
- 所有靴との被り
- `ScoreBreakdown`への導線

`finalScore` / `Decision` / `Demotion`はCoreが出したものを表示するだけにする。UIは再計算せず、判定名を変更せず、注意理由を隠さない。

合う理由・注意すべき理由は、UI-02では表示方針にとどめる。Gemini説明文は表示しない。必要な理由表示は、Coreの`ScoreBreakdown`、タグ、価格・予算相性、`demotions`から後続設計で整理する。

結果画面で表示しないもの:

- 実在価格
- 在庫
- プレ値予測
- 真贋判定
- AI自由推薦
- 外部サイト価格
- 購入リンク
- Gemini説明文

## 11. エラー・空状態

エラー文は短く、ユーザーが次に何を直せばよいか分かる表現にする。エラーは入力項目の近くに表示する。

想定する状態:

| 状態 | UI対応 |
| --- | --- |
| スニーカー名が空 | `スニーカー名を入力してください。`を表示し、次へ進めない |
| 入力金額が未入力 | `金額を入力してください。`を表示する |
| 入力金額が0以下 | `1円以上の金額を入力してください。`を表示する |
| 予算が未入力 | `予算を入力してください。`を表示する |
| 予算が0以下 | `1円以上の予算を入力してください。`を表示する |
| タグが0件 | `特徴タグを1つ以上選んでください。`を表示し、次へ進めない |
| タグが上限超過 | `タグは5個まで選べます。`を表示し、追加できない |
| Coreへ渡す入力が不足 | `診断に必要な入力が不足しています。`を表示し、診断ボタンを無効にする |
| PreferenceProfileがない | `先にPreference Diagnosisを完了してください。`を表示し、診断ボタンを無効にする |
| Core呼び出し失敗 | `診断に失敗しました。もう一度お試しください。`を表示する |

空状態:

- PreferenceProfile未作成時は、この画面から診断結果を出さない。
- 候補入力が空の初期状態では、Step 1の入力欄を表示する。
- 所有靴データがない場合は、所有靴との被りを参考表示として扱う。

## 12. スマホ表示方針

- 1カラムを基本にする。
- 入力ステップを上部に表示する。
- タグは押しやすいチップ形式にする。
- 金額と予算は縦並びにする。
- 確認画面ではカードを縦積みにする。
- 下部の主要ボタンは押しやすい高さにする。
- フォーム入力中に主要ボタンが入力欄を隠さないようにする。
- タグチップは折り返し表示し、横スクロール前提にしない。
- 結果画面では`finalScore`と`finalDecision`を先に見せ、その下に理由、注意、詳細導線を積む。

## 13. アクセシビリティ方針

- タグボタン、次へボタン、診断するボタンはスマホでも押しやすいサイズにする。
- 選択状態は色だけでなく、枠・文字・ラベルでも分かるようにする。
- 無効ボタンは見た目だけでなく`disabled`状態にする。
- ステップ番号だけに頼らず、現在の入力段階をテキストでも表示する。
- キーボード操作でもタグ選択と次へ移動ができる設計にする。
- エラー文は入力項目の近くに表示する。
- タグチップはボタンとして実装する前提にし、選択状態をスクリーンリーダーへ伝える。
- 入力金額と予算には明確なラベルを付け、単位はUI上で分かるようにする。
- 価格注記は小さすぎる文字だけにせず、確認画面でも再表示する。
- `ScoreBreakdown`への導線はリンクまたはボタンとして意味が分かるラベルにする。

## 14. Coreとの境界

### UIが行ってよいこと

- 入力を保持する。
- 入力を`SneakerCandidate`へ変換するための仕様を定義する。
- `budgetFit`の考え方を定義する。
- Coreへ渡すinputの形を整理する。
- Coreの出力を表示する前提を整理する。
- スニーカー名、ブランド、メモをUI表示用データとして保持する。
- 日本語タグラベルを内部`SneakerTag`へ変換する。

Coreへ渡す想定:

```ts
recommendSneakers({
  preferenceProfile,
  candidates: [candidate],
  ownedSneakers,
  preferredTags,
});
```

`candidate`は後続実装で以下の形に変換する。

```ts
type SneakerCandidate = {
  sneakerId: string;
  name: string;
  vector: {
    culture: number;
    styleFit: number;
    simplicity: number;
    street: number;
    volume: number;
    comfort: number;
    durability: number;
    priceLevel: number;
  };
  tags: SneakerTag[];
  budgetFit: number;
};
```

UI-02では、この変換仕様を定義するだけで、変換関数やReactコンポーネントは作らない。

### UIが行ってはいけないこと

- `finalScore`を再計算する。
- `Decision`を変更する。
- `Demotion`を隠す。
- Geminiの文章を理由に判定を変える。
- 市場価格を断言する。
- 在庫や真贋を断言する。
- AIにタグやスコアを作らせる。
- ブランド名やスニーカー名だけでスコアを決める。
- Coreの`priceScore`、`overlapPenalty`、Decision、Demotion仕様をUI都合で変更する。
