# SOLE//MATRIX UI-01: Diagnosis UI Spec

## 1. 診断UIの目的

SOLE//MATRIXの診断UIは、ユーザーが軽い質問に答えることで `PreferenceProfile` の初期値を作る入口である。

このUIは、おすすめスニーカーや購買判断を直接確定しない。診断回答から作るのは、Core推薦ロジックへ渡すための初期 `PreferenceVector`、`PreferencePolicy`、`AxisImportance` であり、最終的な `finalScore`、`Decision`、`Demotion` は必ずCoreが計算する。

UI-01の対象は診断回答体験とPreferenceProfile初期値への変換方針までとする。Gemini Adapterによる説明生成、AI説明表示、Candidate Sneaker Check、スニーカー名や金額からの診断画面は扱わない。

## 2. B2Y風診断体験から参考にする点

参考にするのは、ユーザーが迷わず短時間で完了できる軽い診断体験の構造だけである。

- 8問程度で完了する
- 1画面に1質問だけを表示する
- 回答は3択に絞る
- 進捗が常に分かる
- 前の質問へ戻れる
- スマホでも片手で回答しやすい
- 診断している感覚はあるが、重いフォーム入力にはしない
- 中央カード型の落ち着いたレイアウトにする

## 3. B2Yからコピーしない点

B2Yの文言、見た目、キャラクター、ビジュアル、ブランド表現、診断ロジック、結果表現はコピーしない。

SOLE//MATRIXでは以下を独自設計とする。

- 診断回答はおすすめを直接決めるものではなく、PreferenceProfile初期値を作る材料として扱う
- 質問文はSOLE//MATRIXのCore軸に合わせて設計する
- `finalScore`、`Decision`、`Demotion` はCoreに委譲する
- BUY / WAIT / SKIPなどの判断を診断UI内で作らない
- GeminiやAIに判定を作らせない
- 価格、在庫、プレ値、真贋を診断UIで扱わない
- 性別や属性を固定する質問を避ける

## 4. 画面構成

基本レイアウトは白基調、余白多め、中央カード型とする。画面全体は落ち着いた診断体験に寄せ、情報量を増やしすぎない。

### 4.1 共通要素

- ヘッダー
  - `SOLE//MATRIX` ロゴまたはテキスト
  - 必要なら小さなステップ名として `Sneaker Diagnosis`
- 進捗表示
  - 例: `3 / 8`
  - 例: `8問中3問目`
  - 横長の進捗バー
- 質問カード
  - 質問番号
  - 質問文
  - UI上の短い補足文
  - イラスト枠
  - 回答ボタン3つ
- フッター操作
  - `戻る`
  - `次へ`
  - 最終質問のみ `診断結果を見る`

### 4.2 イラスト枠

各質問カードにはイラスト枠を用意する。ただし、UI-01では具体的な画像生成や画像アセットの制作は必須にしない。

イラスト枠の役割:

- 質問の雰囲気を軽く伝える
- 余白のある診断体験を作る
- テキストだけのフォーム感を弱める

注意:

- 実在ブランドのロゴ、固有スニーカーの意匠、B2Y風のキャラクター表現は使わない
- 質問の答えを誘導しすぎる絵にしない
- 画像が未ロードでも質問と回答は成立する

### 4.3 レスポンシブ方針

スマホでは縦並びを優先する。

- 質問カードは画面幅に合わせて1カラム
- 回答ボタンは縦並びを基本にする
- `戻る` と `次へ` は下部に固定またはカード直下に配置する
- タップ領域を十分に確保する

デスクトップでは中央寄せカードを基本にする。

- カード幅は読みやすい範囲に制限する
- 回答ボタンは横並びまたは縦並びのどちらでもよいが、視線移動が少ない配置にする
- 余白を広めに取り、診断の軽さを保つ

## 5. 8問の質問設計

回答形式は全問共通で「好き / 普通 / 苦手」の3択とする。UI上で `YES / SOSO / NO` のような表現を使う場合でも、内部仕様では必ず以下に対応させる。

| UI表現例 | 内部値 | 意味 |
| --- | --- | --- |
| YES / 好き | `LIKE` | その方向を少し強める |
| SOSO / 普通 | `NEUTRAL` | 大きく変えない |
| NO / 苦手 | `DISLIKE` | その方向を少し弱める |

### Q1

| 項目 | 内容 |
| --- | --- |
| 質問番号 | 1 |
| 質問文 | ハイカットよりローカットが好き？ |
| ユーザーに聞きたい意味 | 足元を軽く見せたいか、日常の服に合わせやすい低めのシルエットを好むかを知る。 |
| UI上の補足文 | くるぶし周りが低く、すっきり見える形のイメージです。 |
| 回答形式 | 好き / 普通 / 苦手 |
| 影響するPreferenceVectorの軸 | 主: `styleFit`。副: `volume` をごく軽く反対方向に調整する。 |
| 影響するPreferencePolicyの軸 | 原則なし。強く「苦手」の場合のみ `explorationTolerance` をごく軽く上げ、ハイカットや存在感のある候補も許容しやすくする余地を残す。 |
| 影響するAxisImportance | 主: `styleFit`。副: `volume` は小幅。 |
| 注意点 | 「ローカット」は `volume` を直接測る質問ではない。ローカット好き = ボリュームがない靴だけが好き、と決めつけない。 |

## 6. 回答形式

回答は全問3択とする。

- `好き`
- `普通`
- `苦手`

内部値はUI文言に依存させず、以下のように扱う。

```ts
type DiagnosisAnswerValue = "LIKE" | "NEUTRAL" | "DISLIKE";
```

UIラベルを `YES / SOSO / NO` にする場合でも、スクリーンリーダーや内部仕様では「好き / 普通 / 苦手」と意味が通るようにする。

回答値の基本方針:

- 好き: その方向を少し強める
- 普通: 大きく変えない
- 苦手: その方向を少し弱める

1問だけで `PreferenceProfile` が極端に変わらないようにする。1問あたりの更新幅は控えめにし、複数回答の積み重ねで傾向が出るようにする。

## 7. PreferenceVector / PreferencePolicy / AxisImportance への変換方針

### 7.1 基本方針

診断回答は `PreferenceProfile` の初期値を作るための入力である。

推奨される変換方針:

- 中立値を `50` 前後に置く
- `PreferenceVector` の1問あたりの主軸更新は小幅にする
- 副軸更新は主軸よりさらに小さくする
- `AxisImportance` は「その軸をどれくらい判断材料にしたいか」を表す
- `PreferencePolicy` は診断質問から直接分かる範囲だけ控えめに動かす
- 値は0から100の範囲に丸める
- 変換後もCoreのスコア計算やDecision判定は行わない

### 7.2 更新幅の目安

実装時の初期案として、以下程度の控えめな更新幅を想定する。

| 対象 | 主軸 | 副軸 |
| --- | ---: | ---: |
| PreferenceVector | +/- 6 | +/- 2から3 |
| AxisImportance | +4 | +1から2 |
| PreferencePolicy | +/- 3 | 原則なし |

`NEUTRAL` は原則として値を動かさない。ただし、回答済みであること自体は状態として保持する。

### 7.3 回答ごとの扱い

- `LIKE`: 対応する方向を少し強める
- `NEUTRAL`: ベースラインを維持する
- `DISLIKE`: 対応する方向を少し弱める

注意:

- `DISLIKE` は反対カテゴリを強く好むという意味ではない
- `LIKE` はその軸だけで候補を確定する意味ではない
- 矛盾する回答があってもUIでは補正しすぎず、Coreに渡す初期傾向として扱う

### 7.4 変換マッピング案

| Question | LIKE時の主な方向 | DISLIKE時の主な方向 |
| --- | --- | --- |
| Q1 | `styleFit` を少し上げ、`volume` をごく軽く下げる | `styleFit` を小幅に下げ、`volume` をごく軽く上げる |
| Q2 | `simplicity` を上げ、`explorationTolerance` を少し下げる | `simplicity` を下げ、`explorationTolerance` を少し上げる |
| Q3 | `street` を上げ、`explorationTolerance` を少し上げる | `street` を下げ、`explorationTolerance` を少し下げる |
| Q4 | `culture` と `styleFit` を上げる | `culture` を下げ、`explorationTolerance` を少し上げる |
| Q5 | `simplicity` と `styleFit` を上げる | `simplicity` を下げ、`explorationTolerance` を少し上げる |
| Q6 | `comfort` を上げる | `comfort` を下げすぎず、重要度だけ小幅に下げる |
| Q7 | `durability` を上げる | `durability` を下げすぎず、重要度だけ小幅に下げる |
| Q8 | `volume` を上げ、`street` を少し上げる | `volume` を下げ、`explorationTolerance` を少し下げる |

## 8. 画面遷移

画面遷移は単純なステップ形式とする。

1. 診断開始
2. Q1
3. Q2
4. Q3
5. Q4
6. Q5
7. Q6
8. Q7
9. Q8
10. Core推薦へ渡す準備
11. 結果表示画面へ遷移

UI-01で定義するのはQ1からQ8までと、Coreへ渡すための入力整理までである。結果表示画面の詳細、AI説明表示、候補スニーカー入力画面は別設計で扱う。

遷移ルール:

- 未回答のまま `次へ` は押せない
- Q1では `戻る` を非表示または無効にする
- Q2以降では `戻る` を押すと前の質問へ戻る
- 戻ったときに前の回答を保持する
- 最後の質問で回答済みになったら `診断結果を見る` を有効化する
- ブラウザ戻るやリロード時の扱いは実装時に別途決めるが、少なくとも同一セッション内では回答保持を優先する

## 9. 状態設計

UI状態は診断回答と画面進行だけに集中させる。

### 9.1 最小状態

```ts
type DiagnosisState = {
  currentQuestionIndex: number;
  answers: Record<QuestionId, DiagnosisAnswerValue | undefined>;
  status: "answering" | "readyToSubmit" | "submitting" | "submitted" | "error";
};
```

### 9.2 保持する状態

- 現在の質問番号
- 各質問の回答
- 回答済み数
- 次へ進めるか
- 最終送信できるか
- 送信中か
- エラー状態

### 9.3 派生状態

- `answeredCount`
- `progressText`
- `progressRatio`
- `canGoBack`
- `canGoNext`
- `canSubmit`

### 9.4 保持しない状態

UIでは以下を保持しない、または保持しても表示用キャッシュに留める。

- `finalScore`
- `rawDecision`
- `finalDecision`
- `demotions`
- Gemini生成文
- 外部価格
- 在庫
- 真贋情報
- プレ値情報

## 10. エラー・空状態

### 10.1 未回答

未回答時は `次へ` または `診断結果を見る` をdisabledにする。エラー文で強く叱るのではなく、ボタンの無効状態と補助テキストで自然に示す。

例:

- `回答を選ぶと次へ進めます`

### 10.2 変換エラー

回答から `PreferenceProfile` 初期値へ変換できない場合は、診断を壊さず再試行できる導線を出す。

例:

- `診断結果の準備に失敗しました。もう一度お試しください。`

### 10.3 Core呼び出し前の候補なし

UI-01では候補スニーカー入力やCandidate Sneaker Checkを扱わない。実装時に候補が空の場合は、診断完了後の結果画面側で空状態を出す。

例:

- `診断は完了しました。おすすめ候補の準備がまだありません。`

### 10.4 画像未ロード

イラスト枠の画像が読み込めない場合でも、質問と回答は利用できるようにする。

- 代替テキストを用意する
- レイアウトが崩れない固定枠を用意する
- 画像未ロードを致命的エラーにしない

## 11. アクセシビリティ方針

- 回答ボタンはスマホで押しやすい大きさにする
- 選択状態は色だけでなく、枠、文字、ラベルでも分かるようにする
- 無効ボタンは見た目だけでなく `disabled` 状態にする
- Question番号だけに頼らず、現在の進捗をテキストでも表示する
- 「好き / 普通 / 苦手」はスクリーンリーダーでも意味が通る文言にする
- キーボード操作でも回答できる設計にする
- 回答ボタンはラジオグループ相当の意味を持たせる
- 現在選択中の回答は `aria-checked` などで分かるようにする
- 進捗バーには視覚表示だけでなくテキストラベルを付ける
- エラー文は該当操作の近くに表示する
- フォーカス移動は質問遷移後に質問見出しまたはカード先頭へ移す

## 12. Coreとの境界

### 12.1 UIが行ってよいこと

- 回答を保持する
- 回答を `PreferenceProfile` 初期値へ変換するための仕様を定義する
- Coreへ渡す入力の形を整理する
- Coreの出力を表示するための前提を整理する
- 回答済みかどうかを判定する
- 進捗、戻る、次へ、送信状態を管理する

### 12.2 UIが行ってはいけないこと

- `finalScore` を再計算する
- `Decision` を変更する
- `Demotion` を隠す
- Geminiの文章を理由に判定を変える
- 価格、在庫、真贋、プレ値を断言する
- 診断結果だけでおすすめを確定する
- Candidate Sneaker CheckをこのUI内に混ぜる
- スニーカー名、タグ、金額から診断する画面をUI-01に含める

### 12.3 Coreへ渡す前提

診断完了後、UIは以下を整理してCoreに渡す。

- `preferenceProfile`
- `candidates`
- `ownedSneakers` がある場合はその情報

UI-01では `candidates` と `ownedSneakers` の入力UIは設計対象外とする。結果表示もCore出力を尊重する前提だけを定義する。
